# OpenAPI Route-Declared Response Precedence

## TLDR
**Key Points:**
- `buildResponses()` in `packages/shared/src/lib/openapi/generator.ts` let metadata-inferred
  error responses (401 from `requireAuth`, 403 from `requireFeatures`) overwrite the responses a
  route documented for the same status.
- The generic fix: an explicitly declared response always wins; auto-generated entries are applied
  last and only for statuses the route left undocumented.

**Scope:**
- `buildResponses()` response-map assembly only. No change to runtime auth behaviour — the OpenAPI
  document is the only artifact affected.

**Concerns:**
- The precedence must hold whether the route declares the status through `responses` or `errors`.

## Problem Statement
`buildResponses()` assembled the response map by iterating route-declared entries first and the
metadata-inferred entries last, assigning `entries[status]` unconditionally:

```ts
for (const res of [...list, ...errorList]) {
  const status = String(res.status || 200)
  entries[status] = { /* ... */ }
}
```

`list` holds what the route declared under `openApi.responses`; `errorList` starts from the
route's `openApi.errors` and then receives the auto-generated 401/403 pushed in from route
metadata. Because those auto-generated entries were appended last and the assignment was
unconditional, they silently replaced a route's own entry for the same status.

The result: a route that documents a meaningful `403` (for example a domain-specific reason) had
the generic *"Forbidden – missing required features"* text published instead, with no signal at
generate time. The same overwrite applied to `401`.

A naive reorder to `[...errorList, ...list]` is **not** a complete fix. It rescues a status
declared under `responses`, but a status declared under `errors` sits in `errorList` *before* the
auto-generated entry, so the auto-generated one still wins on the second pass. The precedence rule
has to be explicit rather than order-dependent.

## Proposed Solution
Separate the auto-generated entries from the route-declared ones and guard their assignment:

- Collect the metadata-inferred 401/403 into their own `autoErrors` list (marked
  `xAutoGenerated: true`) instead of pushing them onto `errorList`.
- Iterate `[...list, ...errorList, ...autoErrors]`. For an entry marked `xAutoGenerated`, skip it
  when `entries[status]` is already set — i.e. when the route declared that status itself, through
  either `responses` or `errors`.

An auto-generated response is a default inferred from metadata; an explicit declaration on the
route is more specific and therefore authoritative. Auto-generated entries continue to fill in
statuses the route did not document, and they keep their `x-autoGenerated` marker so readers of the
document can still tell the difference.

### Design Decisions
| Decision | Rationale |
|----------|-----------|
| Explicit declaration wins over metadata-inferred | An explicit `responses`/`errors` entry is more specific than a default synthesised from `requireAuth`/`requireFeatures`. |
| Guard on the existing `xAutoGenerated` marker | The marker is set only inside `buildResponses`; no route declares it, so it is a safe, self-contained signal that an entry is a default. |
| Apply auto entries last, not first | Keeps the emitted order stable and makes "fill only the gaps" the literal reading of the loop. |
| No warning on collision | A route declaring its own 401/403 is now the intended pattern, so a collision is expected, not a defect to log. |

## Behavioural Notes
- Runtime authorization is unchanged. Only the generated OpenAPI document differs.
- Routes that declared no `401`/`403` still receive the auto-generated entries, unchanged.

## Testing
- `packages/shared/src/lib/openapi/__tests__/generator.test.ts` — exercises `buildResponses`
  through the public `buildOpenApiDocument`:
  - a route-declared `403` via `responses` survives alongside `requireFeatures`;
  - a route-declared `403` via `errors` survives alongside `requireFeatures`;
  - a route-declared `401` survives alongside `requireAuth`;
  - with neither declared, the auto-generated `401`/`403` are still emitted and carry
    `x-autoGenerated`.
- The precedence tests are non-vacuous: reverting the guard turns the three positive cases red
  while the auto-generation case stays green.
